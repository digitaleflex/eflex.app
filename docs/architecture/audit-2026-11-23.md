> **Méthode** : relecture statique du dépôt à l'état de `main` après les PR #193 à #216 (compteurs, fichiers de déploiement, schéma, workflows, ADR, code des chemins critiques). **Aucun accès** au serveur de production, à Coolify, à Redis ou à PostgreSQL réels : tout constat sur le comportement en production est une **déduction du code**, signalée « à vérifier » quand je ne l'ai pas prouvée.

## 2. Architecture actuelle

```
Client ──HTTPS──► Traefik (externe) ──► portail (Next.js, 1 conteneur)
                                           ├─ pages + API (119 routes)
                                           ├─ worker BullMQ (concurrence 2)      ┐ même
                                           ├─ sondes, watchdog, sauvegardes     ├ processus
                                           └─ bus d'événements (SSE)            ┘
              portail ──► PostgreSQL (volume local)   portail ──► Redis (sans persistance)
              portail ──► API Coolify ──► Docker (applications, bases, services des clients)
              portail ──► GitHub (App, webhooks)      portail ──► Kkiapay / FedaPay / Resend
```

Principe fixé par l'ADR-0012 : **le portail est le plan de contrôle, Coolify est l'unique backend de déploiement**, Axiom est gelé.

## 3. Points solides
- **Isolation entre organisations testée** : chaque route doit être classée dans un manifeste et attaquée par des tests inter-organisations (`api-tenant-isolation.integration.test.ts`).
- **Sécurité traitée activement** : audit S1–S9, contrôle du compose client à chaque déploiement, secrets chiffrés (AES-GCM), routes admin en écriture toutes auditées (vérifié : 0 route d'écriture sans `audit()`).
- **Qualité de code** : 0 `any` hors tests, 13 `eslint-disable`, ≈ 1 240 tests, charte visuelle appliquée par un test, accessibilité auditée en CI.
- **Honnêteté du produit** : états « indisponible » plutôt que des valeurs inventées, interrupteurs désactivés par défaut pour tout ce qui n'est pas validé sur serveur.
- **Décisions écrites** : ADR et audits datés ; documentation d'exploitation (sauvegardes, volumes, supervision).

## 4. Constats et risques

### P0 — à traiter avant de grossir
**R1. Point de défaillance unique.** Un seul serveur héberge portail, PostgreSQL, Redis, Traefik, Coolify **et** les applications des clients. Une panne du serveur coupe tout, y compris l'accès aux sauvegardes si elles sont sur la même machine. *Reco* : sauvegarde hors site **restaurée au moins une fois** (#174), puis un second serveur (au minimum pour les sauvegardes et le build, #176).

**R2. Redis sans aucune persistance** (`--save "" --appendonly no`). La file BullMQ des déploiements vit dans Redis : au redémarrage de Redis, les jobs en attente disparaissent. Le watchdog finit par passer les déploiements en échec (30 minutes par défaut), mais le client voit un déploiement « bloqué ». *À vérifier* : si le démarrage ré-enfile les déploiements `pending` depuis la base. *Reco* : soit activer AOF, soit réconcilier au démarrage (relire les déploiements non terminaux et les ré-enfiler ou les échouer tout de suite). Le commentaire du compose dit aussi « sessions » : or `auth.ts` ne branche pas Redis comme stockage de sessions (donc elles sont en base) ; le commentaire est périmé.

**R3. Web, worker et sondes dans le même processus.** `instrumentation-node.ts` démarre le worker et plusieurs boucles (`setInterval` : surveillance, sauvegardes, alertes, watchdog) dans le processus du portail. Conséquences : (a) tout redéploiement du portail interrompt les builds en cours ; (b) un build lourd concurrence l'interface ; (c) **impossible de passer à deux réplicas sans doubler les boucles** (sondes et alertes en double). *Reco* : séparer un conteneur `worker` (même image, autre commande) ; remplacer les `setInterval` par des tâches répétables BullMQ.

### P1
**R4. Réseau Docker partagé entre clients (S5)** : interrupteur livré (`EFLEX_ORG_NETWORKS`), **non validé** sur serveur ; les ressources existantes ne sont pas migrées.
**R5. Limites de ressources non appliquées par défaut** (#131) : une application sans limite configurée peut monopoliser le serveur ; le plafond n'agit que sur la saisie du client.
**R6. Dépendance forte à Coolify** : `lib/coolify.ts` fait 1 954 lignes ; les appels sont concentrés (bien), mais une montée de version de Coolify peut casser des routes sans alerte (sondage de capacités existant, 3 tests). *Reco* : un test de contrat contre l'OpenAPI de la version déployée, lancé en CI à chaque changement de version cible.
**R7. PostgreSQL du portail** : une seule instance, un volume local ; pas de récupération à un instant donné ; la restauration a un script (`restore-test.sh`) mais **aucune exécution consignée** que j'aie pu voir.
**R8. Observabilité absente côté ressources** : pas de source pour CPU, mémoire, disque, réseau (#119–#122) ; pas de traçage ; les journaux sont ceux de Docker/Coolify. Décision proposée : Beszel (`docs/architecture/metriques-sources.md`).

### P2
**R9. Dette de structure.** `lib/` plat de 237 fichiers ; fichiers volumineux : `coolify.ts` (1 954), `project-settings.tsx` (1 175), `worker.ts` (972, le chemin critique de déploiement, **peu testable**, d'où l'absence de test de reprise #160), `schema.prisma` (945). *Reco* : sous-dossiers par domaine (`lib/coolify/`, `lib/billing/`, `lib/monitoring/`…), découper `worker.ts` en étapes pures testables.
**R10. Deux bases de Go à tenir : Axiom (≈ 61 000 lignes, en pause) et Build Fleet (actif, dépôt séparé).** Axiom pèse sur la CI (`go.yml`, `contracts.yml`) et sur la lecture du dépôt ; l'ADR-0009 de Build Fleet pose la règle « un seul moteur Go à terme », aujourd'hui **non respectée**. *Reco* : trancher par un ADR avant la phase 3 de Build Fleet : Build Fleet reprend ou remplace les agents d'Axiom, ou Axiom est sorti dans un dépôt archivé. Ne pas ajouter une troisième chaîne. Une charge de maintenance à surveiller : une personne, trois chaînes (portail, Axiom, Build Fleet).
**R11. Intégration continue.** `main` est resté rouge du 19 au 23 novembre sans que cela bloque les fusions : aucune protection de branche exigeant les vérifications, d'après ce que j'ai observé. 57 branches fusionnées traînent. *Reco* : exiger les vérifications avant fusion, supprimer automatiquement les branches fusionnées.
**R12. Pas de preuve de montée en charge.** Aucun test de charge ; limites de débit distribuées via Redis (donc affaiblies si Redis tombe : repli mémoire par processus, documenté).
**R13. Facturation à l'usage non branchée** (#143) : seuls les calculs purs existent ; aucun débit réel.

### P3
- 13 `eslint-disable`, à relire un par un.
- Documentation publique inexistante (projet `docs.eflex.app` en cours de cadrage).
- `docs/` mélange documents internes et futurs documents publics.
