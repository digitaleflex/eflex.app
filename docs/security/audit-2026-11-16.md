## Détail

### S1 — Évasion vers l'hôte par un compose client (Critique, 9.9)

`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H`

Un client qui déploie son propre `docker-compose.yml` passait le contrôle
`lib/compose-safety.ts`, qui ne refusait que `privileged`, `network_mode: host` et
les montages directs de l'hôte. Il restait possible de :

- déclarer un volume `driver: local` avec `driver_opts: { type: none, o: bind, device: / }`
  : la racine du serveur est montée dans le conteneur (lecture et écriture de tout,
  dont `.env.prod`, les données de tous les clients, la socket Docker) ;
- obtenir des droits noyau (`cap_add: [SYS_ADMIN]`, `devices`, `security_opt:
  apparmor:unconfined`) ou partager les espaces de noms de l'hôte (`pid: host`…) ;
- rejoindre le conteneur d'un autre client (`network_mode: container:…`,
  `volumes_from`) ;
- charger un fichier non vérifié (`include`, `extends.file`).

**Correctif** : toutes ces clauses sont refusées, avec un message clair, à chaque
déploiement (tests de contournement dans `compose-safety.test.ts`).

### S2 — Détournement de trafic par labels Traefik (Haute, 8.7)

`CVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:C/C:H/I:H/A:N`

Le Traefik de l'hôte lit les labels de tous les conteneurs du réseau `proxy`. Un
compose pouvait déclarer `Host(\`eflex.app\`)` ou le domaine d'un autre client (et
obtenir un certificat valide), une règle sans `Host` qui capte tous les sites, ou un
routeur TCP/UDP. Conséquence : hameçonnage sur le domaine de la plateforme, vol de
sessions, interception du trafic d'un autre client.

**Correctif** : les règles de routeur HTTP doivent se limiter, par `Host(...)`, aux
domaines du projet (transmis par le worker) ; routeurs TCP/UDP, plugins et labels
`coolify.*` refusés.

### S3 — Volumes et réseaux externes (Haute, 8.5)

`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:N`

`volumes: { x: { external: true } }`, un `name:` forcé ou un réseau externe
(`coolify`) permettaient de monter le volume d'un autre projet ou de rejoindre ses
réseaux. **Correctif** : seuls le réseau `proxy` du proxy est autorisé comme réseau
existant ; volumes externes, noms forcés et pilotes refusés.

### S4 — Sous-domaines de la plateforme (Haute, 7.6)

Un projet nommé « API » recevait `api.eflex.app`. **Corrigé dans #169**
(`lib/reserved-subdomains.ts`).

### S5 — Isolement réseau entre clients (Moyenne, 6.5)

`CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:C/C:H/I:L/A:N`

Les applications et bases managées sont sur le réseau Docker de Coolify : une
application peut joindre la base d'un autre client par son nom. Les mots de passe
générés limitent le risque, mais tout service sans mot de passe (Redis mal réglé,
interface d'administration interne) devient accessible. **Piste** : une
« destination » Coolify (réseau) par organisation (`/servers/{uuid}/destinations`,
`destination_uuid` à la création).

### S6 — Adresse du client falsifiable (Moyenne, 5.3)

`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N`

`getClientIp` retenait la 1re entrée de `X-Forwarded-For`, choisie par le client :
les limites par IP (inscription, collecte d'audience, webhooks) étaient
contournables. **Correctif** : la dernière entrée, ajoutée par le proxy de confiance
(`TRUSTED_PROXY_HOPS` pour plusieurs proxys). **À vérifier** : Better Auth lit
`x-forwarded-for` avec sa propre logique (`auth.ts`, `advanced.ipAddress`) ; confirmer
sur le serveur que Traefik réécrit cet en-tête (comportement par défaut sans
`forwardedHeaders.insecure`).

### S7 — CSP non appliquée (Moyenne, 5.4)

La politique est envoyée en `Content-Security-Policy-Report-Only` : elle signale mais
ne bloque rien. **Piste** : analyser les rapports, puis passer en
`Content-Security-Policy` (procédure dans `lib/security-headers.mjs`).

### S8 — Horodatage FedaPay (Faible, 3.1)

Un horodatage dans le futur était accepté sans limite. **Correctif** : fenêtre de
±5 min.

## Recommandations hors code

1. Après déploiement du correctif S1–S3, **relancer le déploiement des projets
   compose existants** : ceux qui utilisaient une clause désormais refusée échoueront
   avec un message explicite, à corriger avec le client.
2. Vérifier sur le serveur qu'aucun conteneur client n'a déjà ces clauses :
   ```bash
   docker ps -q | xargs docker inspect --format '{{.Name}} priv={{.HostConfig.Privileged}} caps={{.HostConfig.CapAdd}} pid={{.HostConfig.PidMode}} net={{.HostConfig.NetworkMode}}'
   ```
3. Jeton Coolify : ne lui donner que les permissions utiles (`read`, `write`,
   `deploy`, `read:sensitive`), le renouveler s'il a pu fuiter.
4. Mettre Coolify et les outils de supervision derrière le réseau privé (#169).
