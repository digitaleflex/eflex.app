# AGENTS.md

## Repo map

Ce dépôt fusionne `digitaleflex/eflex.app` (produit EFLEX, TypeScript) et `digitaleflex/axiom` (moteur Go). Cible : console EFLEX → API du moteur Axiom → agent sur les VPS. Voir `README.md` (« Feuille de route de l'unification »).

- `services/engine` — moteur Go (API, analyse, plan, build, exécution, GitHub, secrets, auth, migrations SQL). `cd services/engine && go test ./...` ; les tests d'intégration exigent `AXIOM_TEST_DATABASE_URL`.
- `services/agent`, `services/orchestrator` — modules Go séparés (chacun son `go.mod`).
- `portail/` est l'unique console : les anciennes consoles Axiom `apps/cloud` (Vite) et `apps/client-dashboard` (Next 16) ont été supprimées (#16). Ne pas les recréer.
- `schemas/` (contrats Axiom : `axiom.yaml`, artefacts, experts) ≠ `schema/` (produit EFLEX : `eflex.json`, `schema/v1.json`). Tous deux sont utilisés : ne pas en supprimer un au profit de l'autre. Docs Axiom dans `docs/` (ADR dans `docs/adr`).
- CI : `.github/workflows/` (Go, contrats de schémas, agent, et `ts.yml` pour les packages TS + le portail).

- `packages/detector` — deterministic repo snapshot → `BuildPlan`; no network/LLM/runtime deps. Entry: `src/detect.ts` (`detect`), CLI `src/cli.ts`. `src/walk.ts` expose `walkRepository()` : **source unique** du parcours local et des segments ignorés (`IGNORED_SEGMENTS`), utilisée par le CLI et le renderer.
- `assets/brand/` — sources de marque haute résolution (non servies). Les assets publics restent dans `portail/public/`.
- `packages/renderer` — `BuildPlan` → docker-compose YAML + nginx/env templates. Entry: `src/render.ts`; yaml dependency. `src/dockerfile.ts` génère le Dockerfile, `src/deploy.ts` assemble les artefacts de déploiement (port réel, `build_pack`, `postDeploy` en service one-shot). Le portail les consomme via l'alias `@eflex/renderer` (`lib/deploy-plan.ts`) ; `yaml` est aussi dépendance du portail.
- `schema/v1.json` — authoritative JSON Schema for plans; `schema/test.ts` validates every fixture plan/alternative via Ajv.
- `config/domains.sh` — **source unique** des domaines/URLs publics (un seul `EFLEX_ROOT_DOMAIN`, aucune valeur secrète) ; `scripts/sync-domains.sh` régénère les fichiers statiques qui ne peuvent pas interpoler `${VAR}`.
- `portail/` — Next.js 15 App Router portal (Better Auth, Prisma, Coolify client). **Not** in root pnpm workspace; has own `package-lock.json`; use `npm` there.
- `README.md` (detector behavior), `DEV.md`/`PROD.md` (infra), `schema/README.md` (plan contract).

## Commands (root)

```bash
pnpm install          # pnpm@10, Node >=24
pnpm test             # Vitest (packages TS + modules du portail ; périmètre dans vitest.config.ts)
pnpm typecheck        # tsc detector + renderer only; NOT portail
pnpm detect <dir>     # tsx packages/detector/src/cli.ts
pnpm render <dir>     # tsx packages/renderer/src/main.ts
```

Single test: `pnpm vitest run packages/detector/test/detect.test.ts`; filter test: `pnpm vitest run -t "detects Next.js"`.
`pnpm typecheck:all` couvre détecteur + renderer + portail (avec `prisma generate`). Le portail a aussi `npm run lint` (ESLint `--max-warnings=0`, `.eslintrc.json` ; `next lint` est déprécié). La CI `ts.yml` lance tests, typechecks, garde-fou domaines, `prisma validate/generate`, lint et **`next build`** avec des variables factices.
Portal: `cd portail && npm install && npm run dev|build|start|lint|typecheck`.

Détection dans le portail : `POST /api/projects/analyze` → `lib/repo-analysis.ts` récupère l'arborescence (API GitHub ; dépôts publics via raw.githubusercontent.com, dépôts privés via l'API Contents avec jeton d'installation GitHub App) puis les fichiers demandés, et appelle `@eflex/detector` en boucle. `lib/github-url.ts` valide les URL. Le portail importe le détecteur par alias (`tsconfig` paths + `experimental.externalDir` + `extensionAlias` dans `next.config.mjs`) : **n'importer que des types (`import type`) dans les composants client**. `POST /api/projects` refait l'analyse côté serveur et ne reçoit jamais le plan du client. Les tests de ces modules (`portail/src/**/*.test.ts`) tournent avec `pnpm test`.

Déploiement : `POST /api/projects` crée le projet (variables chiffrées par `lib/crypto.ts`, AAD `projectId:clé`) puis un `Deployment` `queued` enfilé dans Redis (`lib/queue.ts`, BullMQ). Le worker (`src/worker.ts`, démarré par `src/instrumentation-node.ts` (via `src/instrumentation.ts`) si `REDIS_URL`) fait avancer la machine à états `lib/deployment-state.ts` (`queued → analyzing → provisioning → building → deploying → live | failed | cancelled`), traduit le `BuildPlan` via `lib/deploy-plan.ts` et pilote Coolify 4.6 par `lib/coolify.ts`. Il ne gère qu'un service par projet pour les plans générés (un plan multi-services est refusé) ; un dépôt qui fournit son propre `docker-compose.y(a)ml` / `compose.y(a)ml` est déployé comme application Coolify `dockercompose` (voir `docs/architecture/deployment-monorepos-volumes.md`). Un seul déploiement actif par projet (`lib/project-deployments.ts`, y compris webhook GitHub) ; annulation `POST /api/projects/[id]/deployments/[deploymentId]/cancel` (BullMQ + `POST /deployments/{uuid}/cancel`, statut conditionnel) ; watchdog toutes les 60 s qui passe en `failed` après `DEPLOYMENT_TIMEOUT_MINUTES` (30 par défaut). À chaque changement d'état il appelle `announceDeploymentStatus` (`lib/deployment-events.ts`) : événement temps réel et, aux états finals, notifications.

Multi-applications (lot C de D2, #6, drapeau **`EFLEX_MULTI_APP`** désactivé par défaut) : `POST /api/projects` accepte `apps: [{ root, framework?, primary? }]` (1..10), chaque dossier étant **re-analysé côté serveur** au même commit (framework inconnu → 409) ; une `ProjectApp` est toujours créée, même en mono-app. `enqueueProjectDeployment(project, { apps, groupId, commitSha, exclusive, rollback })` crée un `Deployment` par app dans une transaction (même `groupId`, verrou **par app** : une app déjà en cours est ignorée) ; le worker garde 1 job = 1 app et résout plan/root/domaine/nom Coolify via `lib/deployment-context.ts` (`ProjectApp`, miroir `Project.*` pour `position = 0`). Le quota compte les applications (`ProjectApp`, `assertProjectQuota(org, n)`). Routes : `apps` dans `GET /api/projects` et `GET /api/projects/[id]`, `?appId=` sur `POST /redeploy` et `GET /deployments`, suppression en boucle des applications Coolify. `EFLEX_MULTI_APP=0` : `apps` > 1 refusé (403 `multi_app_disabled`), comportement mono-app inchangé. Helper pur : `lib/project-apps.ts` (noms stables, domaine `<slug>-<app>` sur un seul label).

Multi-tenant : tout projet appartient à une organisation (plugin Better Auth `organization`, organisation personnelle créée à l'inscription). Toute lecture ou écriture de projet doit passer par `resolveOrganization(session)` (`lib/organizations.ts`) ; créer ou relancer exige `canManageProjects(role)`. Administration : plugin `admin`, routes `api/admin/**` gardées par `requireAdminApi()` (404 sinon), chaque action appelle `audit()` ; le rôle `admin` vient de `ADMIN_EMAILS` mais seulement pour un e-mail vérifié. Pages admin : `/admin` (indicateurs agrégés + export CSV, `lib/admin-metrics*.ts`), `/admin/live` (flux SSE global + tail d'audit, `lib/live-events*.ts`), `/admin/projects` et `/admin/deployments` (opérations auditées, journaux masqués, réconciliation, déblocage), `/admin/infrastructure` (`lib/infrastructure-health.ts` + réglages `PlatformSetting` : maintenance, inscriptions, annonce). Le mode maintenance de la base bloque les nouveaux déploiements (`lib/project-deployments.ts`) et l'inscription (`auth.ts`) ; `MAINTENANCE_MODE=true` reste prioritaire.

Temps réel : `lib/event-bus.ts` (table `Event`, un interrogateur par processus) alimente `/api/events` (un flux SSE par onglet, filtré par organisation) ; côté client `EventsProvider`/`useEvents`/`LiveRefresh`. Journaux de build en direct : `/api/projects/[id]/deployments/[deploymentId]/logs` (lecture seule, secrets masqués). Notifications : `lib/notifications.ts` (`notify`, préférences type × canal `app`/`email`, anti-doublon par `dedupeKey`) envoie aussi, si `RESEND_API_KEY` est présente et que le canal `email` du type est actif, l'e-mail `notificationEmail` (`lib/email-templates.ts`, liens absolus via `appUrl` de `lib/email.ts`) — un seul envoi par notification réellement créée, jamais bloquant. Tests d'intégration (`organizations`, `events`, `notifications`, `admin`, `logs`) : `EFLEX_TEST_DB=1 DATABASE_URL=… BETTER_AUTH_SECRET=… ENV_ENCRYPTION_KEY=… pnpm test` après `npx prisma migrate deploy` ; sans `EFLEX_TEST_DB=1` ils sont ignorés (la CI définit un `DATABASE_URL` factice). La CI les exécute avec un service PostgreSQL.

Docker : l'image du portail se construit avec la **racine du dépôt** comme contexte (`docker build -f portail/Dockerfile .`), car elle embarque `packages/detector` ; l'allowlist du contexte est dans `portail/Dockerfile.dockerignore`.

Auth: Better Auth (`portail/src/lib/auth.ts` serveur, `auth-client.ts` client, `session.ts` pour `getSession()`). Modèles Prisma `User`/`Session`/`Account`/`Verification` imposés par Better Auth ; le mot de passe e-mail vit dans `Account.password` (hash bcrypt). Variables : `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`. Plugins : `organization`, `admin`, **`twoFactor`** (TOTP + codes de secours, modèle `TwoFactor`), `nextCookies`. Rate limiting partagé en base (`RateLimit`, `rateLimit.storage = 'database'`) + Redis pour les routes applicatives (`lib/rate-limit.ts`, repli mémoire). Gestion des sessions : liste/révocation (`/dashboard/settings` → Sécurité), sessions révoquées au changement de mot de passe. Passkeys WebAuthn : plugin `@better-auth/passkey`, modèle `Passkey`, ajout/suppression dans `SecuritySettings`, connexion par `authClient.signIn.passkey()` (`rpID` = hôte de `BETTER_AUTH_URL`). Comptes liés : `accountLinking.trustedProviders = ['google']`, liste des comptes dans `SecuritySettings` (`linkSocial`, `unlinkAccount`) et premier mot de passe pour un compte Google via `POST /api/account/password` (`auth.api.setPassword`, serveur uniquement). Captcha Cloudflare Turnstile **facultatif** : actif seulement si `TURNSTILE_SECRET_KEY` et `NEXT_PUBLIC_TURNSTILE_SITE_KEY` sont fournies (sinon endpoints vides = plugin inerte) ; la clé publique est passée en build arg Docker. Impersonation admin : `POST /api/admin/users/[id]/impersonate` (refusée pour un admin/soi-même), bandeau `ImpersonationBanner` dans le tableau de bord, sortie `POST /api/admin/impersonation/stop`, deux actions auditées. En-têtes de sécurité : `portail/src/lib/security-headers.mjs`, branché via `headers()` dans `next.config.mjs` (HSTS en production, `nosniff`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, COOP) avec une CSP **Report-Only** (Turnstile et Kkiapay autorisés) à passer en enforce après validation.

Prisma: **une seule source de vérité**, `portail/prisma/schema.prisma` (modèles Better Auth + `Project`/`EnvVar`/`Deployment`/`Subscription`). Depuis `portail/` : `npx prisma generate` / `npx prisma migrate dev` / `npx prisma validate`. Il n'existe plus de schéma Prisma à la racine ; la CI valide le schéma avant `tsc --noEmit`.

Secrets des projets (issue 04) : `portail/src/lib/crypto.ts` chiffre `EnvVar.value` en AES-256-GCM (`v1:<nonce>:<ciphertext+tag>`, AAD `projectId:key`). Clé `ENV_ENCRYPTION_KEY` (32 octets base64) **hors base et hors image Docker**, `ENV_ENCRYPTION_KEY_PREVIOUS` pour la rotation, validation au démarrage via `portail/src/instrumentation-node.ts`, migration/rotation via `pnpm exec tsx portail/scripts/encrypt-existing-env-vars.ts`. Aucune route `GET` ne renvoie de valeur.

E-mails (issue 05) : `portail/src/lib/email.ts` envoie via l'API REST **Resend** (aucune dépendance), `email-templates.ts` pour les gabarits français. `RESEND_API_KEY` + `EMAIL_FROM` (domaine vérifié dans Resend). Better Auth : `emailVerification.sendVerificationEmail`, `sendOnSignUp`/`sendOnSignIn`, `requireEmailVerification` et `sendResetPassword`. **La vérification n'est exigée que si `RESEND_API_KEY` est présente** (sinon aucun compte ne peut être verrouillé sans lien). Pages `/verify-email`, `/forgot-password`, `/reset-password` ; `/api/auth/config` expose l'état à l'interface (`emailEnabled`, `emailVerificationRequired`, `googleEnabled`). Le limiteur de débit **partagé** via Redis (multi-instances) reste à faire ; le limiteur actuel est en mémoire.
GitHub (issue 07) : `portail/src/lib/github-app.ts` (JWT RS256, jetons d'installation, `X-Hub-Signature-256`, deploy keys), `lib/git-credentials.ts` (résolution du jeton : installation App ou PAT), modèles Prisma `GitInstallation` / `GitPat` / `PlatformSetting` / `WebhookDelivery` et champs `Project.repoFullName` / `installationId` / `productionBranch` / `repoPrivate` / `githubDeployKeyId` / `coolifyPrivateKeyUuid`. Webhook **`POST https://eflex.app/api/webhooks/github`** : signature vérifiée, idempotence par `X-GitHub-Delivery`, `push` → `Deployment queued` + file BullMQ avec le SHA. Routes `/api/github/{config,connection,install,installations,repositories,pat}` et manifest admin `/api/github/app-manifest/{start,callback}` ; sélecteur `components/new-project/github-picker.tsx`, carte `components/settings/github-connection.tsx`. `repo-analysis.ts` lit les dépôts privés via l'API Contents avec le jeton court (App) ou le PAT. Le flux manifest stocke les identifiants de l'App chiffrés dans `PlatformSetting` (variables `GITHUB_APP_*` prioritaires, jamais commitées) ; `ADMIN_EMAILS` ouvre le bouton admin. Déploiement d'un dépôt privé : le worker crée une deploy key GitHub (permission `administration:write`) et une clé privée Coolify, puis appelle `/applications/private-deploy-key` ; suppression du projet = suppression des deux clés.

Déploiements asynchrones (issue 06) : file **BullMQ** `portail/src/lib/queue.ts` (`jobId = deploymentId`, `REDIS_URL`), worker `portail/src/worker.ts` démarré par `src/instrumentation-node.ts` (via `src/instrumentation.ts`) (dans le processus du portail), machine à états `lib/deployment-state.ts`. `POST /api/projects` → **202 `queued`** ; `GET /api/deployments/[id]` (statut + logs), `POST /api/projects/[id]/redeploy`, panneau temps réel `components/deployment-panel.tsx` (polling 3 s). `bullmq` + `ioredis` sont dans `serverExternalPackages`. Le worker est idempotent et reprend les jobs après redémarrage. **Instrumentation Next** : tout code Node (crypto, BullMQ/ioredis) vit dans `src/instrumentation-node.ts`, importé depuis `src/instrumentation.ts` derrière un `if (process.env.NEXT_RUNTIME === 'nodejs')` **en ligne** — un `return` anticipé laisse le bundler edge résoudre ioredis et casse `next dev` (500 partout, `string_decoder`, #101).

Réglages du portail : `/dashboard/settings` (profil, mot de passe, changement d'e-mail vérifié, suppression de compte bloquée tant qu'un projet a un `coolifyAppId`) et `/dashboard/projects/[id]/settings` (nom, branche de production, variables d'environnement, suppression). Routes : `PATCH/DELETE /api/projects/[id]`, `POST /api/projects/[id]/env-vars`, `DELETE /api/projects/[id]/env-vars/[key]` ; validation partagée dans `lib/project-settings.ts`. La suppression d'un projet supprime d'abord l'application Coolify (`DELETE /applications/{uuid}`, 404 traité comme déjà supprimé) : un échec annule la suppression locale. `productionBranch` suit la branche modifiée.

Webhooks Resend : URL publique **`https://eflex.app/api/webhooks/`** (alias : `/api/webhooks/resend`), servie avec ou sans slash final (`skipTrailingSlashRedirect`). Signature **Svix** vérifiée par `portail/src/lib/resend-webhook.ts` (`svix-id` / `svix-timestamp` / `svix-signature`, HMAC-SHA256, tolérance 5 min). Secret `RESEND_WEBHOOK_SECRET` (préfixe `whsec_`) dans `.env.prod`, jamais commité. Événements : `email.sent`, `email.delivered`, `email.bounced`, `email.complained`, `email.delivery_delayed`. Route exemptée du mode maintenance.

Axiom (Go) : `cd services/<engine|agent|orchestrator> && go test ./... -count=1 -p 1`. Avec PostgreSQL : `AXIOM_TEST_DATABASE_URL=postgres://axiom:axiom@127.0.0.1:5432/axiom?sslmode=disable`. Tests Docker réels : `AXIOM_TEST_DOCKER=1` (plus `AXIOM_TEST_E2E=1` pour `engine/internal/e2e`). La CI ne les lance que pour le moteur (`./internal/e2e/`, `./internal/build/`), pas pour l'agent. État vérifié du moteur (ce qui est prouvé ou non) : `docs/roadmap/parallel-plan.md`, section « Verified status ».

Docker dans la sandbox cloud : `dockerd` est installé mais à démarrer à la main, avec `HTTPS_PROXY` et sans `--bridge=none` (sans réseau de pont, aucun port ne se publie) : `dockerd --host=unix:///var/run/docker.sock --iptables=false --ip6tables=false --registry-mirror=https://mirror.gcr.io &`. Docker Hub limite les téléchargements anonymes : passer par le miroir. Les `RUN` d'un build qui sortent sur Internet exigent `--build-arg HTTPS_PROXY` (et `--network=host`). Le trafic sortant est intercepté par le proxy : un `RUN pip install` échoue sur le certificat. Pour les tests de bout en bout Python, construire une image de base locale qui fait confiance au proxy (copier `/root/.ccr/ca-bundle.crt` et l'ajouter à `/etc/ssl/certs/ca-certificates.crt`, avec `PIP_CERT`/`SSL_CERT_FILE`) et la nommer `python:3.12-slim-bookworm` : `TestPythonToLive` ne retélécharge pas une image présente. Rien de tout cela ne persiste d'une session à l'autre ; nettoyer avec `docker system prune -af`.

## Detector / renderer rules

- Detection precedence in `detect.ts`: valid `eflex.json` > compose fourni (`docker-compose.y(a)ml`/`compose.y(a)ml`) > `Dockerfile` > monorepo resolution > candidates in `collectCandidates` order; **invalid** `eflex.json` → `plan: null` (no fallback). Un compose gagne sur un Dockerfile car il décrit aussi les services voisins ; `eflex.json` reste l'échappatoire explicite.
- Adding a new framework: register detector in `collectCandidates()` (priority matters) **and** add fixture to `test/fixtures.ts` listed in `allFixtures()`.
- Changing any `BuildPlan` field must update `packages/detector/src/types.ts` and `schema/v1.json`; `schema.test.ts` validates all fixture plans/alternatives.
- Detection is deterministic: inputs are only `RepoSnapshot`; no filesystem or network access inside `detect()`.
- User‑facing detector strings (reasons, warnings, questions) are **French**; keep them French.
- Relative TS imports use explicit `.js` suffixes (ESM, strict TS `noUnused*`/`noFallthroughCasesInSwitch`).
- Renderer maps every framework in `render.ts` (serveurs: `nextjs`/`nuxt`/`node`/`remix`/`solidstart`/`redwoodjs`/`php`/`python` → service `app` ; statique: `static`/`vite`/`astro`/`svelte` → `web` nginx ; `laravel` → `app`+`web`+workers ; `docker`/`eflex-config` → générique) ; framework inconnu → `RenderError`. Réseau externe unifié : `proxy`. Generated compose is parsed as YAML in tests.

## Infra

- Dev: `docker compose -f docker-compose.dev.yml up -d` (Postgres 5432, Redis 6379, MinIO 9000/9001). Coolify peut être local (c'est le cas sur ce VPS) ou distant ; renseigner `COOLIFY_API_URL`/`COOLIFY_API_TOKEN` dans `.env`.
- Client Coolify (`portail/src/lib/coolify.ts`) : API v4.6. Il découvre/crée le projet `COOLIFY_PROJECT_NAME` (défaut `Eflex`) et l'environnement `COOLIFY_ENVIRONMENT` (défaut `production`), crée l'application avec `build_pack=dockerfile` si le dépôt a son propre Dockerfile, sinon `nixpacks` avec les commandes du `BuildPlan`, puis `POST /deploy` et `GET /deployments/{uuid}`. Chaque projet reçoit `<slug>.<PORTAL_DOMAIN>` ; les labels Traefik (`websecure`, réseau `proxy`, `letsencrypt`) sont **réappliqués par PATCH après création**, avec `is_container_label_readonly_enabled=false` pour que Coolify ne régénère pas ses entrypoints `http`/`https`, et `is_auto_deploy_enabled=false` (le webhook Eflex pilote les redéploiements). Après un déploiement `live`, le worker vérifie le certificat TLS réel (`lib/tls.ts`, `waitForTls`), ajoute une ligne `[SSL]` au journal et persiste `Project.tlsValid` / `tlsExpiresAt` / `tlsCheckedAt` ; il ne rétrograde pas un déploiement qui fonctionne déjà. Les plans multi-services (compose app + workers) sont refusés avec un message explicite : Coolify 4.6 ne déploie pas un compose brut sans `docker-compose.yaml` dans le dépôt. Variables optionnelles : `COOLIFY_PROJECT_NAME`, `COOLIFY_ENVIRONMENT`, `COOLIFY_PROJECT_UUID`, `COOLIFY_SERVER_UUID`.
- Page projet : badges **Santé & sécurité** (`lib/project-health.ts`, statut runtime + validité TLS), onglet **Logs** d'exécution (`GET /api/projects/[id]/logs`, Coolify `GET /applications/{uuid}/logs`, secrets masqués), et **Disponibilité & actions** dans les paramètres (`GET/POST /api/projects/[id]/runtime` → `start|stop|restart`, confirmation pour arrêt/redémarrage). Ces routes passent par `resolveOrganization` et `canManageProjects` pour les actions.
- Domaines personnalisés : modèle `ProjectDomain` (hostname unique, `verifiedAt`, champs TLS), routes `/api/projects/[id]/domains` (GET/POST), `/domains/[domainId]` (DELETE) et `/domains/[domainId]/verify` (POST). `lib/custom-domain.ts` normalise et réserve `*.PORTAL_DOMAIN`, puis vérifie le CNAME vers `PORTAL_DOMAIN` ou les A/AAAA du portail. Après vérification, `enqueueProjectDeployment` programme un déploiement ; le worker recompose les labels Traefik (`traefikLabels` accepte plusieurs hôtes) et PATCH aussi `domains` dans Coolify. Maximum 5 domaines par projet, TLS contrôlé par domaine après déploiement.
- Facturation (socle #18) : `Subscription` est **par organisation** (`organizationId` unique), `pendingPlan` conserve une demande en attente, `lib/plans.ts` définit `free/starter/pro/agency` (prix en **FCFA**, limites projets/membres/domaines), `lib/billing.ts` calcule le plan effectif et `assertProjectQuota` bloque la création au-delà. UI : carte **Abonnement** dans `/dashboard/organization` (`/api/billing/summary`, `/api/billing/request`), admin `/admin/organizations` (`POST /api/admin/organizations/[id]/subscription`, audité).
- Maintenance des abonnements (relance #18) : `lib/billing-renewal.ts`, démarrée par `src/worker.ts` (passe immédiate puis toutes les 6 h, verrou par processus), ne facture jamais. `active`/`trialing` échu → `past_due` + 7 jours de grâce (limites du plan conservées) ; fin de grâce → statut `past_due` **maintenu** (créations et nouveaux déploiements bloqués, applications et données intactes, pas de passage en `cancelled`) ; `manualOverride` jamais touché ; paiements `pending` > 24 h expirés. Notifications `billing.grace_started` / `billing.grace_ended` aux rôles owner/admin/billing, `dedupeKey` stable par abonnement + période, lien `/dashboard/organization`. Détails, exploitation et rollback : `docs/operations/billing.md`. Limite connue : un minuteur par instance du portail (pas de verrou distribué) — prévoir un job répétable BullMQ avant de scaler horizontalement.
- Paiements en ligne : `lib/payments.ts` gère **Kkiapay** (widget client + vérification serveur `POST /api/v1/transactions/status`) et **FedaPay** (transaction + token de paiement, webhook signé `t=…,s=…`). Modèle `Payment` (référence interne, montant FCFA, statut, `providerRef`, `invoiceNumber`, champs de remboursement), `/api/billing/checkout`, `/api/billing/kkiapay/confirm`, webhooks `/api/webhooks/{kkiapay,fedapay}`. L'activation est idempotente et prolonge l'abonnement de 30 jours. Factures PDF (`lib/invoices.ts`, `GET /api/billing/invoices/[paymentId]`), historique `GET /api/billing/payments` (expire les paiements en attente > 24 h), page admin `/admin/payments` et remboursements (`POST /api/admin/payments/[id]/refund` : Kkiapay via API, FedaPay manuel confirmé).
